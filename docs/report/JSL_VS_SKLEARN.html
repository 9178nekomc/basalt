JSL vs scikit-learn：主观与客观对比报告（v5 PyTorch 级运行时）

JSL 2.4（Java 21 调度 + Rust 张量引擎/经典核 + jsl.torch + JFR） vs scikit-learn 1.9.0 （Python 3.11 + Cython/OpenMP/LAPACK） 同一份数据、同一组超参、同一台机器；全部数字可由 ./compare.sh 复现。

0. 摘要：v5 改变了什么

v4 把 10 项对比全部拉到持平或反超，但"可扩展性"仍低于 sklearn。v5 不再围绕经典估计器打转， 而是把底层升级成 Java + Rust 的 PyTorch 级运行时：

  1. 21 个原生算子：卷积、池化、BatchNorm、LayerNorm、Softmax、fused CrossEntropy、

GELU/SiLU、Dropout、Embedding、BatchedMatMul、Permute/Reshape。 全部带反向传播，全部通过中心差分梯度检验。

  1. jsl.torch eager API：Tensor、Module、Sequential、Loss、Optimizer，

以及 MultiheadAttention / TransformerBlock。 CNN 端到端训练 100% 准确率；多头 Transformer loss 0.7737 → 0.0053。

  1. Java 独有的编译期布局管线：Sequential<I,O> 把 BCHW → BC → BC 链路钉死，

Conv2d → Linear 在 javac 阶段就失败（InvalidTypedPipeline.java）。

  1. JFR 原生事件流：jsl.NativeQueue 记录每次队列执行的 op 数、字节数、耗时、调用栈，

生产可热附加，Python 没有对应的常开设施。

2.2 直方图减法：这轮怎么省掉一半工作量

朴素直方图提升给每个节点都从样本重新累积直方图。LightGBM 的减法规则是：

分裂节点 N（持有直方图 H_N）为 L/R：
    只对样本数较少的儿子累积直方图 H_small（O(min(n_L, n_R))）
    另一个儿子直接推导：H_large = H_N − H_small（O(特征×桶)，纯内存）

平衡二叉树的每层总累积量从 n 降到 n/2，整体约省 50%；非平衡树节省更多。 JSL 的实现细节：

  • 每棵树的 activeFeatures 固定，父子直方图可直接相减；
  • 直方图对象池（ArrayDeque）复用，深度优先路径上只租还、零分配；
  • 原生直方图会话：分箱矩阵、梯度、Hessian 在 fit 开始时一次性复制进 Rust，

之后每个节点只传样本索引、活跃特征和输出直方图；避免每个节点重复复制 640 KiB 的 bins。会话内部使用 f32 交错桶（gradient/hessian/count 同一 cache line）， 最终增益扫描再提升到 f64；

  • 阈值 samples × features ≥ 50 000 走会话，否则走 Java 并行累积；原生失败自动回退；
  • 分位数分箱也下沉到 Rust：每列 sort_unstable + partition_point，20 000×32 从

58 ms 降到 25 ms；

  • 节点总梯度/总 Hessian 从直方图直接求和，省掉一次样本扫描。

代价是数值上"减法"与"重累积"的浮点求和顺序不同（最后一位量级）， f32 部分和的误差在参考数据上没有改变任何分裂与精度（0.7981 / 0.8867 与 f64 路径一致）。 极端大样本场景仍可用 Java f64 路径对照。

3. Rust 原生内核：底层托管，Java 只做调度

v4 的原生层分两条通道：

Java (jsl.core / jsl.ml / jsl.nativebridge)   ← 参数校验、图编排、回退
        │
        ├── 经典通道：double[] + Get<Type>ArrayElements
        │     ├── Ridge 正规方程（并行 + Cholesky）
        │     ├── GaussianNB 充分统计量
        │     ├── KMeans++ 全流程（双中心 AVX2 距离）
        │     ├── binFeatures（sort_unstable + partition_point）
        │     ├── histogramSession（f32 交错桶 + rayon）
        │     └── forestPredict / dgemm / kmeansAssign
        │
        └── 张量通道：long 指针 + 32B OpCommand + DirectByteBuffer
              ├── Context: slotmap + Arc<RwLock<NativeTensor>>
              ├── CommandQueueBuilder: 一次 JNI 执行整批算子
              ├── Graph: Kahn 拓扑排序 + 逆序反向
              └── SIMD: i→k→j, 6 行分块, AVX2/FMA 8 路

3.1 所有权与释放

  • Java 只持 long 地址；Rust 的 Context 用 slotmap 持有

Arc<RwLock<NativeTensor>>，并用地址索引做 FFI 边界校验。

  • Arc::into_raw 把一份强引用交给 Java；nativeReleaseTensor 命中地址才

Arc::from_raw 并 drop。第二次释放查不到地址，返回幂等状态，不会 double free。

  • Java 侧 NativeTensorHandle 用 AtomicLong + Cleaner 保证 close() 与 GC 兜底

只有一次真正释放；NativeContext 用读写锁保证 context 不会先于 handle 关闭。

  • 没有 Box::leak，没有全局张量池；唯一进程级结构是 context 注册表，不持有张量数据。

3.2 指令队列与自动求导

OpCommand 固定 32 字节：u8 op + 7B padding + u64 input_a + u64 input_b + u64 output。 Java 用 ByteBuffer.allocateDirect 打包，Rust 用 read_unaligned 逐条解析， 在一次 JNI 调用内顺序执行并追加图节点。反向传播从 root 收集可达子图， 用 Kahn 算法拓扑排序后逆序求导；支持 MatMul/Add/Sub/Mul/ReLU/Sigmoid/Tanh/MSE， 以及 NumPy 风格尾部广播的反向求和。原地算子、重复生产、覆盖已消费张量都会在写入前被拒绝。

3.3 SIMD GEMM

前向 GEMM 严格 i -> k -> j，j 最内层；每次处理 6 行，使 6 行 C（约 24 KiB）与 B[k, :] 同时落在 32 KiB L1。AVX2/FMA 8 路并行，运行时检测，非 x86 自动回退标量。

规模Java Vector API (double)Rust f32加速
256³3.16 ms0.37 ms8.4×
512³7.45 ms2.33 ms（115 GF）3.2×
1024³49.60 ms19.62 ms（109 GF）2.53×

原生 MLP（4096×32，32-64-32-8，20 epochs，batch 256，Adam）： 20.0 ms/epoch，最终 MSE 4.2e-4，4096 行推理 7.9 ms。

3.5 PyTorch 级现代训练栈

v5 的 jsl.torch 是 eager API，不是静态 DSL。每个 Tensor 操作立即执行并追加图节点， backward() 在 Rust 侧做 Kahn 拓扑排序和逆序求导。

层实现
算子21 个原生算子：GEMM/广播/卷积/池化/归一化/损失/嵌入/注意力/置换/重塑
模块Linear、Conv2d、BatchNorm2d、LayerNorm、MaxPool2d、Dropout、Embedding
组合Sequential、MultiheadAttention、TransformerBlock
优化器SGD（weight decay）、AdamW（bias correction）、全局 L2 裁剪
损失MSE、fused CrossEntropy（softmax + NLL）
生命周期stateDict() / loadStateDict()、Cleaner、读写锁、幂等释放

编译期信息差：

Sequential<BCHW, BC> net = Sequential.<BCHW>start()
        .add(new Conv2d(ctx, 1, 8, 3, 3))   // BCHW -> BCHW
        .add(new Activation<>(RELU))        // BCHW -> BCHW
        .add(new MaxPool2d(2))              // BCHW -> BCHW
        .add(new Flatten())                 // BCHW -> BC
        .add(new Linear(ctx, 8 * 14 * 14, 10)); // BC -> BC

把 new Linear(...) 接到 Conv2d 之后，javac 直接拒绝；InvalidTypedPipeline.java 是 verify.sh 的强制检查用例。这是动态语言给不了的编译期布局证明。

端到端证据：

  • CNN（8×8 单通道，Conv2d → ReLU → MaxPool2d → Flatten → Linear → CE）：

120 个 full-batch AdamW step，准确率 100%，loss 1.7e-4。

  • 多头 Transformer（dim=8，4 heads，causal mask，pre-norm，GELU FFN）：

40 个 AdamW step，MSE 0.7737 → 0.0053。

  • TorchTestSuite 对 Conv2d、BatchNorm、LayerNorm、Softmax/CE、Embedding、

BatchedMatMul、Dropout、Permute/Reshape 全部做中心差分梯度检验，且 CNN/Transformer 收敛。

5. 信息差：JFR 零开销生产剖析（Python 做不到）

这是"只有我们拥有"的典型：JFR 是 JVM 内置的采样式剖析器，设计目标是生产环境 常开；Python 标准库的 cProfile 是插桩式，开销随 Python 调用粒度放大。

方案基线剖析中吞吐损失
JSL + JFR（常开）93.05 ms92.95 ms−0.11%
Python + cProfile（粗粒度编排）559.8 ms1194.2 ms+113.3%
Python + cProfile（细粒度编排）1059.1 ms2172.1 ms+105.1%

JFR 开启时同时产出 272 KB 的 .jfr 录制文件：方法级热点、分配事件、GC 事件、锁竞争， 且支持 jcmd 热附加到运行中的进程（无需改代码、无需重启）。 Python 侧要么接受 cProfile 的吞吐减半，要么装第三方采样器。对"模型服务 7×24 在线"的 场景，这是决定性的运维差距。

8. 扬长避短：战术总结

  1. 底层托管：张量池、计算图、反向传播、经典核都在 Rust；Java 只做调度与回退。
  2. 零拷贝批处理：128B 指令 + DirectByteBuffer，一次 JNI 执行整批算子。
  3. 算法级省功：直方图减法 + 原生分箱 + 交错直方图桶——最快的代码是不用算的代码。
  4. 并发模型：GIL 逼 Python 用进程；虚拟线程 + 每 context 原生线程池双轨并行。
  5. 运维主权：JFR 常开零开销 + CRC 校验模型容器 + 编译期布局安全。

下一步（按收益排序）：

  1. GBDT 多分类（softmax 多树），复用现有直方图会话；
  2. 稀疏 CSR + 稀疏直方图（文本场景入场券）；
  3. Pipeline 抽象（追上易用性差距的主要抓手）；
  4. 算子融合编译器（把 torch.compile 级的融合也做进来）；
  5. 混合精度/量化：f16/bf16 与 int8 推理。

9. 局限

  1. sklearn 计时波动约 ±10%；HGB 分类 1.03× 处于该噪声带内，不能据此宣称稳定反超。
  2. 直方图减法改变浮点求和顺序；HGB 会话路径的 f32 部分和在参考数据上未改变精度，

但极端大样本/病态梯度下应与 Java f64 路径对照。

  1. 张量引擎使用 f32，经典估计器保持 f64；两者不做隐式转换。
  2. Torch 层为 CPU only：Conv2d groups=1、dilation=1，MaxPool2d 无 padding；

无稀疏/量化/AMP/分布式，也没有 torch.compile 级融合编译器。

  1. 原生库为 Windows x86_64 构建；其他平台需 ./native-build.sh 重新编译。
  2. JFR 对比使用各自平台的标准工具（JFR vs cProfile），未使用第三方采样器。
  3. 评分是作者基于本报告证据的判断，非测量值。
